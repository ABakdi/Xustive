# Evaluation harness

Ranking changes are easy to make and hard to judge. Every weight in `xustive-search::rank` looks
defensible on its own, and a change that improves the three queries someone happened to try can
quietly ruin the rest. This exists so "better" is a number.

```bash
make eval                 # score and write eval/reports/YYYY-MM-DD.json
make eval-check           # score and fail if nDCG@10 regressed against the baseline
./eval/build_golden.py    # regenerate the golden set from the current index
```

## The golden set is machine-judged

`eval/golden/v1.jsonl` was generated by `build_golden.py`, which grades documents by how much of
a query's terms they contain. Every query carries `"judged_by": "machine"`, and every report
prints what share of its score rests on those labels.

**This detects regressions. It does not measure quality.** The judgements partly agree with the
retrieval engine by construction, so a high nDCG here says the engine agrees with a heuristic, not
that it serves Algerian readers well. What it can do — and the reason `M1-T15.4` gates on it — is
notice when a change makes the engine disagree with its own past self.

Two families of query are genuinely not circular, and they are the ones worth watching:

- **Arabizi queries judged against Arabic documents.** The judgement comes from the Arabic form;
  retrieval has to bridge scripts to find it. This is the real test of transliteration.
- **Orthographic variants** — `بجايه` for `بجاية`, `اوت` for `أوت`. Judged on the canonical form,
  queried in the variant, so normalisation has to fold them together.

To upgrade the set, review queries with a native speaker and flip `judged_by` to `"human"`. Reports
count both, so it improves one query at a time rather than needing 200 judgements before it is
worth anything.

## Metrics, and why these

| Metric | Answers |
|:---|:---|
| **nDCG@10** | the headline. The only graded metric, so it distinguishes "the best result moved to position 3" from "a mediocre one did" |
| **MRR@10** | how far a user reads before finding anything useful. Counts grade ≥ 2 only — a near-miss at position 1 is not a success |
| **recall@50** | separates retrieval failures from ranking ones. If recall is low, re-ranking cannot help: the document is not in the pool |
| **zero-result rate** | what users feel most sharply, and what an average hides |
| **per-language nDCG** | an Algeria-first engine scoring well overall while failing on Darija has not done the thing it exists for |

Queries with nothing judged relevant are **excluded** from nDCG and recall rather than scored
zero. Scoring them zero punishes the system for a query nobody judged; scoring them one rewards
it. The count of exclusions is reported.

## The gate

`make eval-check` fails when nDCG@10 falls more than **1 %** relative to the baseline. Relative
rather than absolute, because a point means something different at 0.9 than at 0.2 and the number
moves as the corpus grows.

Re-baselining is deliberate: copy the new report over `eval/reports/baseline.json` and say in the
commit message why the drop was acceptable. A gate that can be silenced by rerunning it is not a
gate.

## Known finding

The first run recorded a **38 % zero-result rate on Arabizi queries** against 0 % for Arabic,
French and English, with nDCG@10 of 0.43 against 0.74–0.84. Transliteration is not bridging to
Arabic documents for well over a third of Darija queries. See `eval/reports/` for the series.
